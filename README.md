# mini-editor

`mini-editor` is a small Rust editor project built for learning how editors work internally. It is not intended to be a production-ready editor. The goal is to keep the codebase small enough to read while still covering real editor concepts such as text storage, anchors, selections, display mapping, commands, and UI integration.

The code in this repository was generated by GPT-5.5. The project also takes inspiration from [Zed](https://zed.dev/), especially in how editor concerns are separated into text, display, editor, project, workspace, and UI layers.

## Goals

- Learn the basic data structures and module boundaries behind a text editor.
- Study how buffers, snapshots, anchors, selections, display rows, and commands fit together.
- Explore how a GUI editor connects low-level text operations to keyboard, mouse, clipboard, scrolling, and rendering.
- Keep each crate focused, testable, and approachable for reading or rewriting.

## Current Features

The project currently includes a minimal GPUI-based editor entry point and several focused crates:

- Rope-based text storage.
- Text buffers and snapshots.
- Anchors that track through edits.
- Undo and redo.
- Multi-cursor and multi-selection editing.
- Display row mapping and soft wrap.
- Search and selection history.
- Mouse, keyboard, clipboard, scrollbar, and rendering paths.
- Project and workspace layers for opening, saving, reloading, and tracking tabs.

This is still a learning project. Treat it as runnable study material, not as a polished editor.

## Crate Layout

```text
crates/
  app/          # Application entry point; starts a GPUI editor window.
  rope/         # Rope text structure, chunks, summaries, and point mapping.
  text/         # Core Buffer, TextEdit, Anchor, snapshots, and undo/redo.
  language/     # Buffer layer with files, language name, diagnostics, and capability flags.
  multibuffer/  # Editable views composed from one or more buffer excerpts.
  display/      # Source offset to display row/column mapping, including soft wrap.
  editor/       # Editor model: selections, movement, editing, search, and history.
  project/      # Project paths, BufferStore, file metadata, save, and reload logic.
  workspace/    # Open editors, command dispatch, tab state, and rendered workspace state.
  ui/           # GPUI view, input, mouse, clipboard, rendering, and scrolling.
```

The rough dependency direction is:

```text
rope -> text -> language -> multibuffer -> display -> editor -> ui
                                      project -> workspace
app -> ui/editor/language/text
```

## Running

Install a Rust toolchain, then run:

```bash
cargo run -p app
```

The entry point is `crates/app/src/main.rs`. It creates an empty local buffer and opens it in a GPUI editor window.

## Building

Build the workspace in debug mode:

```bash
cargo build
```

Build the app crate only:

```bash
cargo build -p app
```

Build an optimized release binary:

```bash
cargo build -p app --release
```

The release binary will be written under `target/release/`.

## Testing

Run all tests:

```bash
cargo test
```

Check compilation:

```bash
cargo check
```

Run tests for a single crate:

```bash
cargo test -p editor
cargo test -p ui
cargo test -p workspace
```

Tests are kept close to the modules they describe, so you can read behavior and implementation side by side.

## Suggested Reading Order

If you want to read the project from the bottom up:

1. `crates/rope/src` - how text is split into chunks and mapped between offsets and points.
2. `crates/text/src` - core buffer edits, anchors, snapshots, and undo/redo.
3. `crates/language/src` - how a text buffer gains file identity, diagnostics, and read/write capability.
4. `crates/multibuffer/src` - how excerpts from buffers become one editable view.
5. `crates/display/src` - how source offsets become display rows and columns.
6. `crates/editor/src` - selections, cursor movement, editing, search, and selection history.
7. `crates/ui/src` - how GPUI events become editor commands and rendered output.
8. `crates/project/src` and `crates/workspace/src` - file state, tabs, save/reload, and command dispatch.

## Questions This Project Helps Explore

- Why does an editor need anchors instead of storing only raw offsets?
- How should anchors move when text is inserted or deleted?
- How can multi-cursor edits avoid overlapping or conflicting selections?
- Should undo/redo record text edits, commands, or higher-level transactions?
- How do soft-wrapped display coordinates map back to source text offsets?
- How do mouse selection, shift selection, and alternate multi-cursor actions converge into one editor model?
- How should an editor detect and respond to external file changes?

## Notes

This repository is AI-generated learning material, inspired by Zed but not affiliated with Zed. It is meant to be read, modified, tested, and broken apart while studying editor internals. A good way to use it is to run the tests, change one module, and then observe how behavior changes across the stack.
